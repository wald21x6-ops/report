Database foundations

Converged DB · Mission-critical · JSON Duality
90 min

Real subject: database systems — the relational model, ACID, normalisation, storage engines. Nail the vocabulary below, then meet the one genuinely novel feature in the whole talk.

Learn

ACID, normalisation, indexes (≈45 min, any decent primer — you likely have most of this). Then read one blog for each side of “polyglot persistence vs converged.” There's a real argument here and Oracle only tells you their half; Snowflake, Mongo and Databricks all disagree, partly on technical grounds and partly on commercial ones.

JSON Relational Duality · the same rows, two shapes

One store, one source of truth. Read it as normalised tables, or as a nested JSON document — Oracle keeps them in sync and lets you write through either. Flip the view:

Hands-on · 20 min

In Postgres (Supabase free tier is fine) make a users table and a users_json view returning the same rows as nested JSON. You just hand-rolled read-only Duality. Now try to make it writable — you'll fail, and that failure is exactly what Oracle is selling.

CREATE TABLE users (id int PRIMARY KEY, name text, team_id int);

-- read the same rows as one JSON document per user:
CREATE VIEW users_json AS
SELECT id, jsonb_build_object(
         'id', id, 'name', name, 'team_id', team_id
       ) AS doc
FROM users;

SELECT doc FROM users_json;         -- works
UPDATE users_json SET doc = '...';  -- fails: views aren't writable.
-- Making THAT writable is what JSON Duality sells.
Done when
You can explain in one sentence why a converged DB is a tradeoff, not a free win.
You gain one engine to run, secure and back up — but you give up tuning each workload on a specialist engine, so no single capability is best-in-class.

Vectors & embeddings

“Vector DB” · information retrieval + a little linear algebra
90 min

An embedding turns a chunk of text into ~1000 numbers where distance ≈ meaning. Similar text lands close together. Search becomes geometry.

Cosine similarity · drag the vectors

Cosine similarity ignores length and measures angle: 1.0 = same direction (same meaning), 0 = unrelated, −1 = opposite. Drag either arrowhead.

Tiny semantic search · type a query

A toy “embedding” ranks these 6 sentences by meaning, not keywords. Try coffee, weather, or money — notice matches with none of your words.

The unglamorous truth: a “vector database” is not a category of database — it's an index type. Postgres has it (pgvector), Oracle added it in 23ai, Mongo added it, everyone added it. Exact nearest-neighbour search doesn't scale, so you use ANN (approximate) via HNSW or IVF indexes: they trade a little accuracy for enormous speed by not checking every point. Pinecone and Weaviate exist because incumbents were slow — and that window is closing.

Hands-on · 25 min

Run pgvector on Supabase. Embed 20 sentences, query the nearest 3. ~20 lines of Python. That's the whole concept.

# pip install psycopg2-binary sentence-transformers
from sentence_transformers import SentenceTransformer
import psycopg2
m  = SentenceTransformer('all-MiniLM-L6-v2')   # 384-dim embeddings
db = psycopg2.connect("dbname=postgres"); cur = db.cursor()
cur.execute("CREATE EXTENSION IF NOT EXISTS vector")
cur.execute("CREATE TABLE docs(id serial, txt text, emb vector(384))")

for s in ["...your 20 sentences..."]:
    cur.execute("INSERT INTO docs(txt, emb) VALUES (%s, %s)",
                (s, m.encode(s).tolist()))
db.commit()

q = m.encode("hot drink in the morning").tolist()
cur.execute("SELECT txt FROM docs ORDER BY emb <=> %s::vector LIMIT 3", (q,))
print(cur.fetchall())          #  <=> is cosine distance
Done when
You can say why HNSW trades accuracy for speed, and roughly how.
HNSW builds a layered graph of shortcut links and greedily hops toward the nearest vectors, visiting only a tiny fraction of the data — so it may occasionally miss the true nearest, but runs in roughly log time instead of scanning everything.
03

RAG, NL2SQL & agents

Select AI · deep research · RAG · privacy agent
2 hours

Real subject: applied LLM engineering — the module closest to what you already build. Most of it is industry-standard; Oracle's contribution is putting NL2SQL inside the SQL engine.

Why NL2SQL is hard — the interesting part no vendor deck admits. The model must know your schema, your business definitions (“active customer” = ?), and it fails silently: a wrong query returns a confident, plausible, wrong number. Demo schemas are clean; real ones aren't. Benchmark accuracy (Spider, BIRD) sits far below the demo on messy real-world schemas.

Watch it guess · one question, many “right” answers

Ask an ambiguous question over a 3-table schema. There's no bug here — each reading is defensible, and the model just picks one and hands you a confident number. That's the failure mode.

Hands-on · 30 min

You've built MCP servers — build a tiny NL2SQL tool over a 3-table SQLite schema, then ask it “how many active users?” and watch it guess. That single experiment teaches more than the whole talk.

import sqlite3, anthropic
schema = "users(id, status, last_login) | subscriptions(user_id, state) | orders(...)"

def ask(question):
    prompt = f"Schema:\n{schema}\nReturn ONE SQLite query for: {question}"
    sql = anthropic.Anthropic().messages.create(
        model="claude-sonnet-5", max_tokens=300,
        messages=[{"role": "user", "content": prompt}]
    ).content[0].text
    print("SQL the model chose:\n", sql)
    return sqlite3.connect("app.db").execute(sql).fetchall()

ask("how many active users?")   # which definition of 'active' did it pick?
Done when
You can explain to a non-technical person why NL2SQL demos always work and NL2SQL products often don't.
Demos use a clean schema the model was shown; real products hit messy schemas and ambiguous business terms, so the model silently picks one plausible reading and returns a confident, wrong number.
04

Lakehouse & open table formats

AI Lakehouse · Iceberg · “end data lock-in”
90 min

Real subject: data engineering — the 20-year arc from warehouse → lake → lakehouse, and why an open table format is now the political center of the whole industry.

Row store vs columnar · why analytics loves columns

Query: SELECT AVG(salary) FROM employees. A row store must read every field of every row to reach one column. A columnar store (Parquet) reads only the salary column. Watch what each has to touch:

The politics: Iceberg is a metadata layer over Parquet files in your own object storage that adds ACID transactions, schema evolution and time-travel to a pile of files in S3. If your data lives in open Iceberg tables, any engine — Oracle, Snowflake, Databricks, DuckDB — can read it, and switching vendors stops being a two-year migration. That's why “end data lock-in” is on the slide. Every vendor now claims to love Iceberg; every vendor also wants you running their engine on it. Oracle putting it up is defensive, not generous.

Hands-on · 20 min

DuckDB locally: read a Parquet file, run a GROUP BY, feel how fast columnar is. Optional: PyIceberg on local files for time travel.

# pip install duckdb   →  then, in Python or the duckdb CLI:
import duckdb
duckdb.sql("""
    SELECT dept, AVG(salary) AS avg_pay, COUNT(*) AS n
    FROM 'employees.parquet'
    GROUP BY dept
    ORDER BY avg_pay DESC
""").show()
# Columnar: only the dept + salary columns are read off disk.
Done when
You can explain what a table format adds that a file format doesn't.
A file format (Parquet) stores bytes efficiently; a table format (Iceberg) adds a metadata layer over many files giving ACID transactions, schema evolution and time-travel — turning a pile of files into a real, queryable table.

Autonomous DB & multicloud

ADB · Autonomous AI DB · AI Multicloud · “manage how you want”
60 min

Real subject: cloud architecture & managed services. The automation is genuinely good; the word “autonomous” is doing marketing work; “multicloud” is a distribution strategy.

The managed-service trade · drag the dial

Moving from self-hosted → fully managed. Nothing is free: every notch you gain on ops, you pay for somewhere else. Slide it.

Why multicloud exists: enterprises already standing on Azure won't move — so Oracle moved to them (Oracle Database@Azure and friends put Oracle DB inside AWS/Azure/GCP data centres). It's distribution, not generosity.

Hands-on · 15 min

Oracle Cloud Always-Free includes 2 Autonomous Databases. Spin one up, run one query, and note how long it took vs docker run postgres. That comparison is the lesson.

# local, self-managed: up in seconds, but you patch/tune/back it up
time docker run --rm -d -e POSTGRES_PASSWORD=x postgres

# managed (OCI Always-Free): provision an Autonomous DB in the console.
# Minutes to start — but you never patch, tune, or back it up again.
# THAT trade (time + control vs. zero ops) is the whole module.
Done when
You can state one concrete situation where autonomous / managed is the wrong choice.
When you need deep, unusual tuning or must avoid lock-in and egress cost — e.g. a latency-critical workload that needs custom storage/kernel config the provider won't expose.

Security, DR & ZDLRA

Security in the age of AI · “end data risk” · ZDLRA
60 min

Real subject: data security & business continuity. Learn two acronyms properly — they are the vocabulary of the entire field — then see why RAG makes an old security problem harder.

RPO & RTO · the two numbers that define disaster recovery

RPO = how much data you can afford to lose (the gap back to your last good copy). RTO = how long you can be down. Drag them and watch the cost story. ZDLRA's whole pitch is pushing RPO to ≈ 0.

The genuinely-new bit: prompt injection, and the fact that RAG breaks row-level security. Your database carefully enforces who can see which rows — but if your vector index contains chunks a user isn't authorised to see, your chatbot will cheerfully retrieve and leak them. The access control lived in the DB; the embeddings escaped it. Read one article on RAG + access control.

Done when
You can explain why RAG makes an old security problem harder.
RAG copies data into a vector index that lives outside the database's row-level security, so a retrieval can surface chunks the asking user was never authorised to see.
Module 0 · the answer
  1. JSON RELATIONAL DUALITY — a real, novel feature. The same data, live-editable as tables and as documents. Not a rebrand.
  2. ZDLRA — Zero Data Loss Recovery Appliance. Actual purpose-built hardware that ships redo logs continuously so RPO ≈ 0. No direct competitor equivalent.
  3. SELECT AI — a real product integration: NL2SQL living inside the SQL engine itself, even though NL2SQL isn't Oracle's invention.

Everything else — vector DB, RAG, converged DB, lakehouse, Iceberg, multicloud, autonomous, privacy agent, deep research — is an industry concept with an Oracle sticker. Learn it once, and it transfers to every vendor on earth.
